# Backlog maintenance rules

This is the authoritative update and review procedure for [OpenBando backlog](BACKLOG.md). AGENTS and README link here; keep procedural changes here rather than adding competing instructions elsewhere. The backlog's lifecycle table is the status quick reference. Archived working plans and audits preserve dated evidence, not current state.

## One repository, one backlog

Each backlog owns the work of its own repository and nothing else (single responsibility). Dependencies point one way: a repository may wait on what it uses, never on what uses it.

- **Here.** A record tracks a change made in this repository. Its next action is a step taken here, and its closure criteria are things this repository's PRs, CI, releases or human checks can show.
- **Upstream** (a library, a service, the harness template): a record may wait on a release there. It is Blocked, names that release and links the issue or PR there.
- **Downstream** (repositories that use this one): a record never waits for them to adopt a change. It closes when the change is released here; each of them records its own adoption in its own backlog.
- **Evidence from elsewhere** can verify a record: a trial in a real consumer, an upstream fix reproduced. Record it in Verification once it has happened; never leave it as a condition still waiting on that repository.
- Link another repository's record when it matters; never track its status here.

Test: if a record's next action or closure condition can only happen in another repository, it is in the wrong backlog. Move that part to the backlog it belongs to and link it.

### Ownership rejection and dependency direction

Reject an active record during review if its Issue, next action or closure criteria assign work to a different repository. Split that work into the owning repository's backlog and retain only an upstream dependency link or dated evidence here. A downstream adoption reminder is still foreign work when hidden in details, labelled a follow-up or placed after the release step. Check all three places, not only the title. This is a semantic review requirement; the layout validator does not establish ownership.

Apply single responsibility and dependency inversion to architecture and delivery: a reusable master/template/library owns generic contracts and behaviour; derived projects depend on those contracts through their own adapters or configuration. A master must not import derived-project implementation, require its private state or deployment, or make its release, acceptance or closure wait for downstream adoption. Required regression tests use repository-owned fixtures and contract tests. An already completed consumer trial may be cited as evidence; it never becomes a pending downstream release gate. Product-specific requirements stay in the product repository.

### Solution coordinators

An optional solution repository owns architecture/contracts, compatibility, coordination and end-to-end integration acceptance. It may legitimately depend on its component releases; this is composition, not a reusable master depending on derived consumers. Components retain their own implementation records and close them on their own acceptance. The coordinator's next action can be defining a contract or running integration checks, never doing a foreign repository's implementation under its own ID. Use the [solution profile](agents/solution-profile.md) and qualified `Components` links. Generated dashboards are read-only snapshots, preserve source ownership/revisions and report missing sources as unknown; never edit copied statuses or average completion percentages. A generic harness release uses its own fixtures and never waits for a real coordinator to adopt it.

## When to update and review

- A plan or promise given to the user (steps, a table to build, a later fix) is recorded at once: a new record or the next action of an existing one, in the same change as the reply that makes it. A plan that lives only in the conversation is forgotten.
- Every code, documentation or asset change and every PR updates the affected bug/feature records. Add a stable ID if needed; maintenance-only changes belong in Other changes. Do not create a new product ID for each follow-up PR.
- At PR creation, add its actual link and distinguish implementation, investigation, partial fix and verification. Replace temporary PR placeholders once the PR exists.
- After a PR merges, when CI/verification finishes, when the user supplies acceptance or a new failure, and at the start of work on a related item, reconcile the affected records using the procedure below.
- When asked for backlog status or an audit, review every active record. During ordinary work, review related items and any contradictions encountered; a row's age alone is never evidence that it is fixed, abandoned or invalid.
- Review and repairs require an active agent execution host. Session-start freshness checks report merged changes, branches, newer harness releases and missing/stale/blocked audit areas; remote fetch failures remain explicit. The daily read-only maintenance workflow also checks review evidence. Follow the [audit procedure](agents/audit.md) for scope-aware dated reports. Audit age warns by default and fails when `audit.enforce` is enabled; malformed audit metadata and enabled maintenance receipt gates fail independently. Never claim automatic repairs or continuous agent review from scheduled checks alone.
- Parallel PRs all edit the backlog, so when one merges the others often conflict there. Resolve in the conflicting PR (AGENTS allows a conflict-only push to a green PR): keep every record from both sides, keep the newer header and move it to the current `main` with the CI of the PRs merged since. Never resolve by taking one side whole.

## Review procedure

1. Read current main and preserve the user's edits. Identify every item affected by the PR/change, including shared dependencies and maintenance records. Reject foreign-repository actions and downstream completion gates under Ownership rejection and dependency direction before publishing.
2. Check the actual PR target, merged state, commit and CI jobs (`npm run ci:status -- <PR numbers>` lists each job, failed and retried tests, and PRs not based on main). Read failures or selected test results when needed. A merge is not verification; a green workflow only establishes checks it actually ran. Skipped jobs, mocked devices and captured screenshots do not establish the behavior they did not test.
3. Compare acceptance requirements, status, next action and verification evidence. Remove obsolete present-tense pending claims after their checks pass; move relevant earlier failures to PR / evidence as labelled history. Record unresolved checks explicitly. If a requirement is ambiguous, investigate rather than invent acceptance or claim closure.
4. Choose the supported state using the lifecycle legend. Implemented means required checks remain. Verified requires all recorded acceptance checks to pass with dated evidence; when every one of them is automated (the PR's own tests and CI, as for tooling and record changes), the merged PR's green CI run is that evidence: cite it. Close only a Verified record, or a cancelled or superseded one with its reason; a reconcile may verify and close in one edit, naming the run. When no action remains, record the resolution and close/archive; agents need no extra permission unless the item explicitly requires human acceptance. Failed checks return the item to Open/Investigate as appropriate; record a named blocker only when it actually prevents the next action.
5. Reassess Human action required and blockers. Yes means the next action depends on explicit human acceptance, a human decision (choosing an option or a scope), private session evidence or real devices. When an agent asks the user to decide before continuing an item, set that item's cue to Yes in the same change, naming the decision; set it back once answered. No means an agent can advance the next step, not that the item is done. Do not require a human for ordinary coding or automated/browser checks. A blocked row states the missing input/dependency and the condition for resuming.
6. Update PR/evidence, verification, next action and Reviewed together. Check related rows for contradictions, such as a passed check still described as pending, a Verified item awaiting a required human check, or a completed maintenance change left yellow indefinitely.
7. Validate table structure, markers, links and dates before publishing. Add the actual follow-up PR link, and reconcile again when its checks finish or it merges: a PR's records name it by number: write "this PR" only until the PR exists, then replace it with `#N` and push at once (on the PR's CI run `check-backlog` fails on a placeholder the branch adds, and on any already on the default branch, where it would fail every other PR), and a record that said "close when this PR merges" is verified and closed in that reconcile. A conflict in the backlog is merged record by record (`node tools/merge-backlog.mjs`).

Staleness prompts review, not a status change by itself. During a full review, flag unresolved dependencies, outdated PR placeholders, missing next actions, old pending claims and long-held Verified records. Keep the last honest evidence date if no new check ran; Reviewed may advance only after actually reviewing the row. Do not reset Opened or fabricate implementation/verification dates to make a record look current.

## Procedures and tracked outcomes

Record agreed outcomes and unresolved work when accepted, before implementation. Routine required steps (reading relevant code/rules, running applicable checks and reviewing ownership) belong to the procedure, not a separate bug/feature each time. Put an item's required acceptance checks in its Check recap/details; a failed check or deferred required action updates that item with the blocker, evidence and next action. A separately owned outcome gets its own record; never duplicate the same work as checklist IDs.

Mandatory means applicable steps must be completed or an actual blocker recorded; it does not turn optional integrations into prerequisites. Capability assessment at setup or relevant workflow changes can conclude that existing tools suffice. MCP/skill recommendation and installation remain conditional on useful missing capability and authorization. An impact map covers actual derived outputs; a separate conflict map is warranted by meaningful unresolved rule/interface conflicts, not required as an empty artifact for every project. See APPLY.md in the template repository for the application trigger matrix.

## Record and evidence requirements

- Keep IDs stable and in ID order within each section; never reuse an ID for a different item. A new finding about the same behaviour as an existing record (a failed check, a follow-up, a regression) goes into that record, reopened if it was closed, not under a new ID. Opened is the first known date that ID entered the ledger, not a guessed original-report date. Preserve it through reopening. Existing audited IDs began on 27 October 2026; later IDs keep their actual dates.
- Each item records a reproducible trigger/request, scope, next action and closure requirements. Active records show the stable ID heading and a bold title, then a five-column signal table (Signal, Priority, Status, Effort, Complete). Keep the human-action line and the Issue / Reproduce / Check table visible for every bug and feature, regardless of actor or whether the record changed. Put the full Next action / closure evidence and the PR history, Opened, Verification and Reviewed metadata in one closed-by-default details block. Priority measures impact: P1 data integrity/reliable CI/core simulator behavior; P2 important workflows/visual defects; P3 enhancements/narrower review.
- PR / evidence identifies actual changes or checks with links and labels. Use `—` if no PR is known. Link latest relevant evidence without discarding important historical context.
- Verification records date, method, result and evidence separately from Reviewed. Methods: Human, Unit/integration, Browser/accessibility, Real-device and Documentation. Use Pending where applicable; different checks may have different dates. Verification states the current result: one entry per method, the latest check of it. Earlier results (a failure since fixed, a superseded pass) belong in PR / evidence, labelled with their PR or run, so the cell never reads “Pending; … passed” for the same check. A unit test does not prove visual/field behavior, and an overall CI result does not replace checking which jobs ran.
- Reviewed is when status/evidence were actually reconciled, not an inferred merge date. Preserve existing dated history; do not invent dates.
- The human-action line is visible in every active record, icon first: `🧑 **→ Human action required: Yes**<br />One short sentence naming the human action or decision.` or `💻 **→ Human action required: No**<br />One short sentence naming the next action.` Keep that sentence short; long plans belong in details. Immediately below it, every record has a two-column table under `| | |` / `|---|---|`, with exactly three rows: `| **Issue** | … |` (the problem or request), `| **Reproduce** | … |` (where and how to trigger it, or the workflow to exercise for a feature), `| **Check** | … |` (observable acceptance criteria or the decision options). No actor or untouched-record exemption. One manual review can cover related IDs; reference the shared item. A `---` line follows every record’s details.
- Effort estimates remaining work, including investigation and verification: `🟢 Small` (up to one focused day), `🟡 Medium` (two to three days), `🔴 Large` (four or more days). Colour always accompanies the word. Complete is a coarse estimate, `~N%` (0–100, multiples of 10), based on the recorded scope and evidence, not measured time or a status mapping. Recalculate and update both estimates whenever the bug/feature changes or collateral work changes its scope, dependencies, implementation or verification; review related records in the same change. Re-estimate from remaining tasks and acceptance evidence, never by incrementing a percentage mechanically. Record the date, rationale and any changed scope in details; if the estimates remain valid, explicitly record that reassessment. Keep pending human/device work in the remaining effort. Pending acceptance prevents 100%; a high estimate never establishes verification or permits closure.

## Visual cues and table integrity

| Cue | Rule |
|---|---|
| First-column status | 🔴 Open · 🟠 Investigate · 🟡 Implemented · 🟢 Verified · 🟣 Blocked · 🔵 Closed; match the written Status. |
| Active priority | 🔺 P1 · 🔶 P2 · 🔹 P3; keep its written label and value. |
| Closed or Blocked priority | ◻️ P1 / ◻️ P2 / ◻️ P3; only the marker changes. Verified priorities retain colour until Closed. |
| Reopened or unblocked | Restore the colour for the retained priority; preserve ID, Opened and previous evidence. |

Colour never replaces status text, priority labels or evidence. Table rows must be contiguous: a blank line terminates a Markdown table. Every table row needs its own header's number of cells: five for active signal rows, two for metadata, and the original width in historical archives. Escape literal pipes inside cells. Use `<br />` for an in-cell line break. Keep a blank line before a table and after its last row. Validate all affected rows, not just the added row, and check local links and status/priority consistency. For documentation-only changes these structural checks and a deliberate review are sufficient; do not invent application test coverage.

## Closure and archives

Close fixes after their recorded criteria pass and no action remains; Verified is a transition, not a permanent holding pen. Human/device acceptance is required only where specified. Cancelled, duplicate or superseded items can close without a verified implementation when the reason and replacement link, if any, are explicit. Do not close a reported bug simply because one attempt could not reproduce it without recording the investigation and remaining uncertainty.

Move closed records, including completed maintenance-only changes, into the year's archive, `docs/archive/backlog-<year>.md` (one file per year, the year the record closed), linked from the active ledger. Inside it records follow their closing date, under a `## Closed <YYYY-MM-DD>` heading per day; records closed before this layout (27–29 October 2026, tables) keep a heading of their own and their original table formats. Preserve each complete record (visible actions plus metadata), with original ID/priority, PR history, evidence, resolution and closure date (`Closed YYYY-MM-DD` in its evidence). An archive only grows: add records anywhere and corrections as dated notes, but never change or remove a line already on the default branch; a record may move from one archive file to another, never out of the archives. `check:backlog` compares every line with the default branch (a line no longer in its file must be in another archive file) and fails on a record whose closing year is not its file's. Write an archive by reading it fully first, never by truncating it. Preserve the bug/feature human-action field when archiving newer records; older archives need not invent missing historical fields. Historical Closed records keep their closure cues if an item is later reopened; the active record describes the new work and links its prior history.

Closing a documentation audit or recording change does not close a product/media feature whose checks remain pending. Put that pending work on its own active item rather than keeping the completed maintenance entry yellow indefinitely.

## Documentation consistency

README summarizes capabilities; AGENTS directs repository work, with per-area rules in [docs/agents/areas.md](agents/areas.md); this file owns backlog maintenance procedure; BACKLOG holds current records and the quick lifecycle legend. Design-system guides own application UI conventions and explicitly scoped component exceptions; mascot/wordmark guides own art requirements. User instructions take precedence. Dated archives, audits and draft articles preserve context and do not override current rules. Generated guide pages follow the tour/generator source; regenerating Markdown does not regenerate clips.

When changing shared rules, reconcile linked summaries and component exceptions in the same PR. Scope the app no-emoji rule to application UI: repository backlog markers are permitted. Scope red navigation/selection exceptions explicitly; do not generalize them into new UI colours. Keep historical evidence dated rather than rewriting it as current verification.

Derived things (generated pages, translations, recordings, guides) follow the impact map, `impact` in `.harness.json`, chains included (`after`): `check:freshness` lists the rows a branch sets off in run order, and each is done in the same PR or recorded with its reason; `docs/agents/impact-map.md` shows the whole map. The check below covers what the map does not.

For **every modification**, including a backlog-only edit, check README, AGENTS and its area notes, BACKLOG, BACKLOG-RULES, design-system/component guides and applicable mascot/style guides for affected claims, rules, links and exceptions. Update every affected document in the same PR; do not edit an unaffected file merely to mark it reviewed. Preserve user changes. State the consistency check and any outstanding discrepancy in the PR validation notes. A backlog state/evidence change can require README or guide corrections even when application code did not change.

On every change or review, actively reassess whether each affected bug/feature status, next action, human dependency, blocker, verification result/date and PR evidence can advance. When the next action is authorized and feasible, perform it; do not merely rewrite an “Agent can…” reminder or stop at a review. Continue agent-owned checks/implementation and close items whose criteria pass. Pause only for an actual dependency or missing required human evidence, record it explicitly, and continue independent authorized work. Never advance a state without the required evidence.

For the active record layout, validate one signal table per stable ID, a bold visible title, exactly one visible human-action paragraph, the complete visible recap, and one closed details block containing Next action and complete metadata. Reformatting must preserve content, dates and evidence; it is not verification of the product.

Run `npm run check:backlog` after every ledger edit. CI validates active signal widths, effort colours and words, estimated percentages and rationale, visible titles, human cues and all three recap rows on every record, collapsed next actions and metadata, dates, unique IDs, status/priority cues and balanced details. Historical archives remain outside this active-layout schema.

Human-action cues identify the next actor: 🧑 Yes requires a human; 💻 No is agent-owned and does not mean complete. Keep the written Yes/No and recap; do not infer status or priority from this cue. Validate cue/value agreement. Historical archives retain their original cues.

The icon comes first, then the arrow and the field label with its value in bold: `🧑 **→ Human action required: Yes**<br />Recap` or `💻 **→ Human action required: No**<br />Recap`. Keep this line and its recap above details; Next action belongs inside details. End every record with a `---` line. Historical archive layouts remain unchanged.
